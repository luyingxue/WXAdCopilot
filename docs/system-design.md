# 微信视频号量化投流助手（WXAdCopilot）系统设计

**版本：** v3.0

**日期：** 2026-07-27
**状态：** 架构基线，后续讨论持续更新

微信官方平台的认证、页面和接口行为统一记录在
[微信平台外部依赖契约](./weixin-platform-dependency-contract.md)；本文件只保留
系统级决策，不重复维护平台细节。

**实施进度（2026-07-26）：** 第一阶段桌面骨架已形成可运行版本。官网浏览保留微信小店带货助手、电商罗盘和加热平台；视频号助手已从运行系统退役。账号 SQLite、登录恢复、三端官网容器和 Mac ARM64 开发打包已完成首轮验证。

## 1. 产品与架构定位

WXAdCopilot 是一款运行在客户电脑上的商业桌面软件。客户使用一台长期在线的 Mac 或 Windows 电脑，在软件内完成多账号官方后台浏览、数据采集、量化分析和投流辅助决策。

系统分为四个部分：

1. **官网浏览**：管理多个运营账号，在软件内打开微信小店带货助手、电商罗盘和加热平台。
2. **投前分析**：监控视频自然表现，判断是否值得投流以及适合的投流时机。
3. **投中监控**：跟踪投放消耗与效果，给出继续观察、加投或止损建议。
4. **投后复盘**：结算成交、退款和净 ROI，复盘策略并优化后续投流判断。

官网浏览模块是后三部分的基础，负责账号、登录态、官方页面和采集运行环境。

## 2. 已确定的架构原则

- **本地优先**：业务数据、浏览器登录态、采集任务和分析过程默认留在客户电脑。
- **一体化桌面软件**：不依赖云中控、Supabase、远程采集 Worker 或 Redis。
- **账号与平台隔离**：不同运营账号使用独立、持久化的浏览器 Session；同一账号的微信小店带货助手与电商罗盘共享必要的 Store 登录态，加热平台保持独立。
- **认证统一、页面隔离**：同一账号、同一身份域只有一个权威 Session。官网页面和后台请求执行器共享完整 Session，但使用互相独立的 `WebContentsView`，采集不得导航、刷新或调试用户正在浏览的页面。
- **跨平台**：使用同一套代码支持 macOS 和 Windows。
- **模块化单体**：第一阶段不拆微服务，但浏览器、采集、存储和分析之间必须保持清晰边界。
- **默认只读采集**：自动采集不得创建、修改、暂停或终止任何官方平台业务对象。涉及投流操作时必须另行设计权限、确认和审计机制。
- **可演进**：未来可增加云同步、团队协作、客户自有 VPS 节点或复杂 Python 分析，但不能影响本地核心运行。

```text
┌──────────────────────────────────────────────────────────────┐
│                   WXAdCopilot 桌面应用                        │
│                                                              │
│  ┌────────────────────────────────────────────────────────┐  │
│  │ React 产品界面                                         │  │
│  │ 账号管理｜官网浏览｜投前｜投中｜投后｜运行状态          │  │
│  └────────────────────────────────────────────────────────┘  │
│                              │ IPC                            │
│  ┌───────────────────────────▼────────────────────────────┐  │
│  │ Electron 主进程                                        │  │
│  │ 窗口管理｜账号 Session｜WebContentsView｜权限与安全      │  │
│  └───────────────┬───────────────────────────────┬────────┘  │
│                  │                               │           │
│  ┌───────────────▼──────────────┐  ┌────────────▼─────────┐ │
│  │ 官方后台浏览器工作区          │  │ 本地核心进程          │ │
│  │ Talent / Compass / Promote   │  │ 调度｜采集｜存储｜分析 │ │
│  │ CDP / 页面 Hook / 登录状态    │  │ SQLite｜任务与健康状态 │ │
│  └──────────────────────────────┘  └──────────────────────┘ │
└──────────────────────────────────────────────────────────────┘
```

系统运行时可以包含多个进程，但对用户表现为一个桌面应用：

- **Electron 主进程**：掌握窗口、浏览器 Session 和安全权限。
- **产品界面进程**：只负责展示与用户交互，不直接访问 Cookie 或数据库文件。
- **官方页面进程**：承载不可信的远程网页，与产品界面和本地能力隔离。
- **本地核心进程**：执行调度、数据采集、SQLite 写入和分析任务，避免阻塞界面。
- **可选 Python 分析进程**：未来复杂统计、回测或机器学习需要时按任务启动，不管理浏览器登录态。

## 4. 技术选型

| 层级 | 选型 | 决策 |
|---|---|---|
| 桌面运行时 | Electron | 提供 Mac/Windows 一致的 Chromium、Session 和桌面能力 |
| 产品界面 | React + TypeScript | 构建账号管理、浏览器框架和分析看板 |
| 构建工具 | Vite | 用于产品界面开发与构建 |
| 官方页面容器 | `WebContentsView` | Electron 当前推荐的内嵌页面方案，不使用已废弃的 `BrowserView` |
| 登录态隔离 | Electron persistent Session | 每账号两个身份域：Store 与 Promote；Talent/Compass 共享 Store |
| 本地核心 | Node.js / TypeScript utility process | 负责调度、采集编排、存储和基础分析 |
| 本地数据库 | SQLite | 单机业务数据存储，启用 WAL 和 Schema migration |
| 浏览器采集 | 独立隐藏 `WebContentsView` | 与官网页面上下文隔离，共享账号完整 Session，不复制 Cookie |
| 自动化测试 | Playwright | 覆盖桌面端到端测试和原生视图生命周期 |
| 复杂分析 | 可选 Python sidecar | 仅在统计、回测、机器学习确有需要时引入 |
| 图表 | 后续在界面设计阶段确定 | 暂不锁定具体图表库 |

### 4.1 为什么选择 Electron

本系统必须在软件内部稳定运行多个官方后台，并让 Mac 和 Windows 具有尽量一致的网页兼容性、Cookie 行为及采集能力。Electron 自带统一 Chromium，比依赖不同系统 WebView 的方案更适合这一核心需求。

### 4.2 Python 的长期位置

Python 不负责官方页面、Session 或浏览器采集，避免同一账号维护两套登录环境。投前阶段的快照差分、流速、分位数和规则判断可由 TypeScript 完成。

如果后续需要复杂统计建模、策略回测或机器学习，则通过稳定的任务契约调用随安装包发布的 Python sidecar。Python 不直接拥有数据库写权限，分析结果由本地核心校验后入库。

## 5. 官网浏览模块

### 5.1 账号模型

系统中的“账号”是一级业务对象。一个账号代表一套隔离的运营环境，并关联：

- Commerce 微信小店带货助手；
- 电商罗盘；
- Promote 官方后台；
- 投前、投中和投后数据；
- 三个平台各自的登录状态。

同一账号的微信小店带货助手与电商罗盘共享 Store Session，加热平台使用独立
Session。三个页面的登录状态分别检测和展示。

### 5.2 多账号工作区

建议的基础交互模型：

```text
左侧：账号与分组
顶部：当前打开的账号标签
主区域：官方页面 / 投前 / 投中 / 投后
状态区：登录状态、采集状态、最后更新时间和异常提醒
```

用户选择账号后，可以直接在系统内浏览并操作官方后台，也可以切换到该账号对应的分析页面。

账号列表必须显示登录健康状态：

- **在线**：该账号要求检查的平台均处于有效登录状态；
- **部分离线**：微信小店带货助手、电商罗盘、加热平台中至少一个登录失效；
- **离线**：该账号要求检查的平台均未登录或登录失效；
- **检测中 / 未检测**：正在检查或尚无有效检测结果。

界面提供“一键刷新”按钮，可主动检查全部账号的三端登录有效性。检测过程必须是只读的，不得改变页面业务状态；检测完成后记录各平台状态、检查时间和失败原因，并立即刷新账号列表。

### 5.3 Session 持久化

- Session 分区名使用系统生成的内部账号 ID 和固定平台代码，不使用昵称等可变字段。
- 当前分区版本为 `wxad_v3`：`persist:wxad_v3_<accountId>_store` 与
  `persist:wxad_v3_<accountId>_promote`。
- 每个身份域由唯一 `IdentityContainer` 管理，Electron Session 是运行时
  唯一事实源。
- 关闭和重新打开软件后，Cookie、LocalStorage 和缓存应继续存在。
- 删除账号属于敏感操作，必须明确提示是否同时删除本地 Session 和业务数据。
- Cookie、Token 和完整请求头不得写入 SQLite、普通日志或分析数据。
- 应用自身确需保存的敏感配置使用操作系统提供的安全存储能力。
- 官方 Session Cookie 由身份容器写入系统加密的冷启动日志；只在页面稳定或
  退出时读取，启动时仅补回当前 Session 缺失项。不得清空后恢复、覆盖、
  合并、去重或在运行中持续反写。
- 禁止健康检查通过新建页面和导航来“验证”登录。

### 5.4 页面导航

系统为每个平台提供固定官方入口和正常浏览能力：

- Commerce 微信小店带货助手：`https://store.weixin.qq.com/talent/`
- 电商罗盘：`https://store.weixin.qq.com/compass/home`
- Promote 视频号加热平台：`https://channels.weixin.qq.com/promote/pages/platform/`

外部跳转、弹窗、新窗口、下载和深链接必须经过统一导航策略处理。只有明确允许的官方域名可以继续使用当前账号 Session。

## 6. 采集架构

### 6.1 核心原则

采集器是独立于官网浏览页面上下文的后台能力：

1. 任务服务向 `AccountRuntime` 申请目标平台能力；
2. `AccountRuntime` 路由到 Store 或 Promote `IdentityContainer`；
3. 身份容器以自己的唯一 Session 创建独立、不可见的请求执行器；
4. 通过官方请求客户端直接调用白名单只读接口；
5. 完成 Schema 校验、去重和时间标记；
6. 写入 SQLite；
7. 关闭采集进程并更新任务与登录健康状态。

官网浏览的 React 宿主节点在应用生命周期内必须保持挂载。模块切换只能覆盖界面并切换 WebContentsView 的原生可见性，不得销毁宿主节点、压缩到 `0×0`，也不得反复从窗口视图树拆装。

### 6.2 与现有研究成果的衔接

实现时需保留第一阶段研究确认的特殊处理：

- wujie 微前端可能需要正确的导航或单次刷新才能 bootstrap；
-部分页面存在 CDP response body 缓冲淘汰问题；
-电商罗盘需要轻量 `JSON.parse` Hook 获取解密后的业务对象；
-不同页面对 `SNAP`、`RELOAD` 的容忍度不同，必须按平台适配；
-任何会卡住微前端的网络拦截方案不得直接用于生产采集。

这些差异应封装在各平台 Adapter 内，不能散落在界面或调度代码中。

### 6.3 分层边界与依赖方向

系统采用模块化单体，依赖只能由上向下：

```text
Renderer UI
    ↓ IPC
Application Services
    ↓
Domain / Task State
    ↓
Platform Gateways
    ↓
Account Runtime
    ↓
Infrastructure
```

各层职责如下：

| 层 | 负责 | 禁止 |
|---|---|---|
| Renderer UI | 展示、输入、触发用例 | 读取 Cookie、直接访问平台接口、直接写 SQLite |
| IPC / Composition | 参数校验、调用应用服务、组装依赖 | 编写投前规则、解析平台响应 |
| Application Services | 执行业务用例、组织事务、保存结果 | 创建页面、管理 Cookie、拼装微信请求 |
| Task Engine | 同账号任务排队、互斥、优先级和运行日志 | 理解平台字段或分析指标 |
| Platform Gateway | 官方接口白名单、账号上下文、响应标准化 | 读写业务数据库、决定是否投流 |
| Identity Container | 单身份域 Session、官网页面、隐藏执行器、状态机 | 导出/改写 Cookie，理解投放业务 |
| Browser Workspace | 原生视图挂载、可见性、尺寸和导航按钮 | 创建 Session、检测登录、访问平台接口 |
| Account Runtime | 身份域路由、任务互斥、生命周期 | 理解投前/投中/投后业务 |
| Infrastructure | SQLite、安全存储、日志、系统能力 | 反向依赖业务或界面 |

核心约束：

1. 一个账号只能由一个 `AccountRuntime` 管理。
2. Store 身份域包含 Talent 与 Compass，共享一个 Session；Promote 使用独立 Session。
3. 上层只能申请平台能力，不能复制 Cookie 或自行创建认证环境。
4. 可见官网页面与隐藏请求执行器共享 Session、隔离页面上下文。
5. 同账号同身份域的登录、检测和采集任务串行执行。
6. Gateway 输出标准快照，不把微信原始结构泄漏给业务层。
7. 所有运行日志必须包含 `accountId`、`taskId`、模块和阶段。

### 6.4 调度模型

调度器运行在本地核心进程中，根据账号、视频状态和投放状态产生任务。任务至少包含：

- `account_id`
- `platform`
- `task_type`
- `target_id`
- `scheduled_at`
- `priority`
- `attempt_count`
- `status`

调度策略属于业务配置；采集 Adapter 只负责执行，不自行改变投前、投中或投后的业务规则。

## 7. 本地数据架构

SQLite 是唯一的本地业务事实源。第一阶段启用：

- WAL 模式；
- 外键约束；
- Schema migration；
- 写入事务；
- 唯一约束和幂等写入；
- 定期备份及恢复校验。

建议按职责分为：

```text
账号与平台状态
  accounts
  platform_sessions

采集运行
  collection_tasks
  collection_runs
  collection_errors

业务实体
  videos
  campaign_orders
  products

时序事实
  video_snapshots
  order_snapshots
  commerce_snapshots

分析结果
  derived_metrics
  recommendation_signals
  strategy_versions
```

具体字段和归因模型将在对应业务模块设计时确定。现阶段不把视频级 GMV直接定义为订单级 GMV，避免同一视频多笔投放时发生重复归因。

## 8. 投前、投中、投后扩展边界

### 8.1 投前

依赖官网浏览模块提供罗盘登录态。主要计算自然播放流速、流速变化、完播表现、
互动表现和带货转化。

#### 已确认的数据刷新流程

1. 快照机每30分钟按最近14个自然日直接请求罗盘 List；开发调试时也允许
   用户手工请求近14天或本月；
2. List 返回范围内全部视频及其当前累计基础、观看和互动快照；
3. 新视频的挂车状态记为 `unknown`，首次逐条请求 `getFeedDetailInfo`：
   - 有 `product.productId` 标记为 `cart`；
   - 无 `product.productId` 标记为 `no_cart`；
4. 后续刷新时，`cart` 视频继续请求详情以更新累计带货快照，
   `no_cart` 视频永久跳过详情；
5. 视频、挂车状态以及内容、互动、带货快照在同一事务中更新到 SQLite。
6. 快照机发现挂车视频的 `productId` 在本地商品表缺失时，按需触发一次
   橱窗商品列表同步；商品同步批量更新 `products`，投前查询再通过
   `videos LEFT JOIN products` 补齐佣金比例。浏览分析页面只读数据库，
   不触发外部接口。
7. 商品列表同步直接分页调用带货助手接口，并从当前 Session 的 Cookie
   补齐官方请求所需的 `biz_magic`、`talent_magic` 请求头；不通过滚动、
   点击或 DOM 解析采集。
8. 商品资料表保存商品全称、短标题、店铺、推广状态和当前佣金比例；商品经营
   分析按 `account_id + product_id` 关联本地全部历史挂车视频的当前投影，汇总
   视频覆盖、点击、成交、退款、净成交和估算净佣金。经营数据由用户手工全量
   刷新，不与商品资料刷新混用；Excel 同时导出明细和计算口径。

投前采集器设置业务接口白名单，只允许：

```text
feed-feedlist-shopfinder-realtime
getFeedDetailInfo
```

两者均在已登录罗盘 Session 的隐藏执行器中直接调用前端请求客户端。隐藏执行器
加载 `/compass/feed/list` 仅用于读取官方 `selectedAccount` 和建立请求客户端，
不会点击、导航或拦截用户正在浏览的官网页面；随后只调用上述两个白名单接口。

在单页不超过 100 条的常规近14天/本月范围内：

```text
本次请求数 = 1 次罗盘 List + 本次需要刷新的详情视频数
```

使用匿名测试账号实测：

- 本周首次：12 条视频，13 次请求；
- 本周再次：7 条挂车、5 条未挂车，8 次请求；
- 本月首次扩展：45 条视频，41 次请求（跳过已知未挂车 5 条）；
- 本月再次：28 条挂车、17 条未挂车，29 次请求。

除罗盘 List 与 `getFeedDetailInfo` 外，其余接口均退出投前运行链路。详细输入、
输出和数据口径见 `docs/data-interface-capabilities.md`。

#### 统一快照模型

投前采集不维护观察池、入池或出池状态。采集层对最近14天发布的全部视频
持续拍照；投前分析从完整时序数据中动态选择样本。

- `snapshot_runs`：一次拍照批次、统一时间戳、范围、请求数量和结果；
- `video_snapshots`：一条视频在一次批次中的一行完整快照；
- List 与 Detail 标准字段合并到同一行；
- 同行保存 `list_raw_json` 与 `detail_raw_json`，用于字段追溯和重新解析；
- `NULL` 表示接口未返回或不适用，`0` 仅表示官方明确返回零；
- `videos` 保留视频档案及最新状态投影，分析历史以 `video_snapshots` 为准；
- 金额统一按“分”使用整数保存，读取时再换算为元，避免长期计算中的浮点误差；
- 历史拆分的基础互动快照表和带货快照表已经退役，完整事实只写入
  `video_snapshots`，确保同一视频每轮采集只有一个统一时间戳；
- 账号基准每日更新一次，结果同时保存算法版本和特征版本，便于历史分析复现；
- 账号首次手工快照成功后启用自动快照；未建立罗盘账号上下文的测试账号不会
  被调度器反复唤醒。
- 自动任务按自然半小时分桶，同账号同时间桶最多一个成功批次；手工补拍不受
  此限制。

第一阶段分析由用户手工发起。未来自动预警只增加分析触发器，不改变快照机。

投前第一个页面是只读的“最新视频快照”：只查询本地 SQLite，显示最近一次
完整批次及快照机状态。页面不得提供范围切换或手工采集按钮，也不得因进入、
切换账号或轮询展示而访问微信接口。

#### 流量曲线分析 v1

- 以发布后的半小时年龄对齐视频，不按自然时间比较；
- 基线优先使用最近60天、最近30条具备至少16个早期节点的挂车视频；
- 挂车有效样本不足20条时使用混合试算基线；
- 计算P25/P50/P75；有效样本达到30条后显示P90；
- 当前视频与账号生命周期参考带叠加，输出当前分位、最近2小时斜率和趋势；
- 有效基线不足20条只显示试算或样本不足，不输出正式投放建议；
- 分析引擎位于独立纯计算模块，不访问 Electron、SQLite、官方平台或页面；
- 投前看板只读取真实账号快照，不提供模拟数据入口，也不使用模拟数据替代真实账号结论。

### 8.2 投中

增加 Promote 订单采集和 Commerce 视频成交变化。初期输出辅助决策和告警，不自动修改官方订单。

### 8.3 投后

增加成交与退款回补、净 GMV、净 ROI 和策略复盘。订单级精确归因必须在多订单重叠规则得到验证后再定义。

四个模块共享账号、Session、调度、采集、SQLite 和运行健康基础设施，不各自实现一套底层能力。

## 9. 安全设计

- 产品界面与官方远程页面使用不同的 WebContents。
- 官方页面必须启用 sandbox、context isolation 和 web security。
- 官方页面不得获得 Node.js、本地文件系统、SQLite 或任意 IPC 权限。
- Preload 仅暴露最小、白名单化能力，不暴露通用执行接口。
- 默认拒绝非必要的摄像头、麦克风、通知、定位和剪贴板权限；扫码登录等必要能力按明确场景授权。
- 导航和新窗口按官方域名白名单控制。
- 日志自动脱敏，不记录 Cookie、Token、签名或完整请求头。
- 自动化业务操作与只读采集分离；未来若开放操作，必须增加用户确认、审计日志、幂等和失败恢复。

## 10. 跨平台发布

一套代码生成 Mac 和 Windows 安装包。

首批正式支持目标：

- macOS Apple Silicon；
- Windows x64。

根据商业需求再补充 macOS Intel 或 Windows ARM。

发布体系从项目初期即包含：

- Mac 应用签名与 Apple notarization；
- Windows 代码签名；
- 平台独立安装包；
- 自动更新；
- 开机自启；
- 应用异常恢复；
- 数据目录升级与迁移；
- SQLite 和 Session 备份；
- 双平台持续集成与基础冒烟测试。

所有运行数据必须使用 Electron 提供的用户数据目录，不依赖固定盘符、用户主目录字符串或本机 Chrome 安装路径。
