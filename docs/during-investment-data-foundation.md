# 投中决策数据基座

## 1. 文档目的

本文定义投中智能盯盘、规则引擎、模型训练和自动操作共同使用的数据基座。
核心目标不是保存一张订单结果表，而是完整保存：

```text
订单条件 → 时序事实 → 智能判断 → 人工/自动操作 → 最终结果
```

任何未来模型都必须能够重放某一历史时刻：只使用当时已经产生的数据，重新得出
当时可做出的判断，禁止使用未来数据造成标签泄漏。

## 2. 事实数据来源

投中快照机每30秒对活动订单执行：

```text
1 × searchFeedPromotionOrderList
1 × getFeedPromotionOrderDetail / 活动订单
```

两个接口均通过账号隔离的加热平台登录环境直接请求，不依赖页面点击或网络拦截。
订单进入最终结束状态后停止高频采集。

只有实际发现订单的轮询才写入数据库。未发现订单和请求失败只写运行日志，
不制造空批次或失败批次；没有活动跟踪订单的账号每5分钟执行一次发现，
存在活动或结算中订单时保持每30秒采集，直至订单进入最终结束状态。

### 2.1 订单主表 `promote_orders`

一笔订单一行，保存整个投放期间基本不变或只需保留最新投影的数据：

- 账号、订单和视频身份；
- 商品身份与订单固定佣金比例；
- 投放目标、时长、出价和扣费方式；
- 预算；
- 下单、预计开始、实际开始、预计结束和实际结束时间；
- 当前订单状态。

佣金比例在订单首次匹配商品库时固化到订单主表。投中期间即使商品库佣金变化，
历史订单也继续使用下单时口径，避免历史盈亏被重算。

### 2.2 时序事实表 `promote_order_snapshots`

一笔订单在一个时间点一行，唯一键为：

```text
account_id + promotion_id + captured_at
```

保存官方累计事实：

- 资金：累计消耗、支付、退款微信豆；
- 流量：累计加热曝光；
- 互动：点赞、评论、收藏、分享和关注；
- 转化：商品点击 PV/UV、下单、支付、净支付；
- 交易：下单金额、支付金额、净支付金额；
- 官方 ROI；
- 当时订单状态；
- 采集质量与缺失字段。

微信豆按十分之一豆、GMV 按分使用整数保存，显示和计算时再转换，避免浮点误差。
原始 Detail 响应只保留14天用于接口追溯，结构化事实永久保留。

### 2.3 差值视图 `promote_order_snapshot_deltas`

累计事实不可直接表示速度。差值视图按订单和时间排序，通过相邻快照计算：

- 真实时间间隔；
- 区间消耗；
- 区间曝光；
- 区间点击；
- 区间支付与净支付；
- 区间净支付金额。

同时识别累计计数回退。出现回退时，该区间差值不可直接用于训练或实时判断，
需要标记为官方修正，不得简单截断为零。

## 3. 智能决策与操作闭环

### 3.1 决策表 `promote_decisions`

一次模型或规则判断一行：

- 通过 `snapshot_run_id + promotion_id` 外键精确关联产生判断的事实快照；
- 保存依据快照时间和判断时间；
- 判断时间；
- 建议：继续、观察、调整、暂停或停止；
- 风险等级与置信度；
- 标准化原因代码和自然语言解释；
- 策略版本与特征版本；
- 建议有效期。

策略版本和特征版本必须保存。否则模型升级后无法解释历史建议，也无法公平比较
不同策略效果。

### 3.2 操作表 `promote_actions`

一次人工或自动操作一行：

- 关联订单及触发该操作的决策；
- 请求和实际执行时间；
- 操作者类型及身份；
- 操作类型和参数；
- 执行状态；
- 官方返回结果和失败原因。

智能建议不等于操作。必须分别记录“系统建议了什么”和“负责人最终做了什么”。

## 4. 模型输入特征

模型不得直接消费未经定义的整包 JSON。训练和在线推理应从结构化事实生成一致的
版本化特征。

### 4.1 静态特征

- 账号；
- 商品及商品类别；
- 佣金比例；
- 投放目标；
- 预算和时长；
- 出价、扣费和定向方案；
- 视频发布时间到投放开始的间隔。

### 4.2 当前累计特征

- 已消耗及预算消耗率；
- 累计曝光、点击、支付和净支付；
- 累计 GMV、净佣金和净盈亏；
- CTR、点击支付转化率、CPC、CPM、佣金 ROI。

### 4.3 多窗口时序特征

建议至少同时生成5、15、30和60分钟窗口：

- 消耗速度及加速度；
- 曝光、点击和成交速度；
- CTR、转化率和 ROI 的滚动值；
- 净佣金增速与消耗增速之差；
- 连续无点击、无支付时长；
- 指标波动和趋势斜率。

所有速度必须使用实际 `interval_seconds` 归一化，不能假设快照一定严格间隔60秒。

### 4.4 状态和质量特征

- 当前订单状态及进入该状态的持续时间；
- 距最后成功快照的时间；
- 最近窗口缺失率；
- 是否发生累计计数回退；
- 是否存在长时间采集间断。

数据过期、严重缺失或计数回退时，系统应停止生成可执行建议，只报告数据风险。

## 5. 标签与效果评价

训练标签必须围绕某个历史决策时刻定义，而不是只看订单最终赚钱或亏损。

可逐步建设的标签：

- 继续投放未来5/15/30分钟的增量净利润；
- 在当前时刻停止相对继续投放节省或损失的金额；
- 建议执行后的净利润改善；
- 达到盈亏平衡所需时间；
- 最终净利润、最大过程亏损和预算利用率。

停止操作后的订单仍可能继续消耗和结算，因此标签窗口必须延续到官方最终结束，
不能以点击停止按钮作为订单终点。

## 6. 缺失值和重采样规则

- 原始快照永不插值、永不覆盖；
- 连续金额和流速可在分析数据集中按规则重采样；
- 点击、支付等离散事件只能认定发生在两个快照之间，不能伪造成小数事件；
- 长缺口不得插值；
- 首条快照没有差值，只能作为累计起点；
- 部分快照和计数回退区间默认不参与训练。

## 7. 在线决策输出规范

每次成功快照后，在线引擎应输出：

```text
recommendation
risk_level
confidence
reason_codes
explanation
valid_until
policy_version
feature_version
```

驾驶舱只展示仍在有效期内、且数据新鲜度合格的建议。超过两个正常采集周期没有
新数据时，建议自动失效，操作按钮不得继续使用旧建议。

## 8. 建设顺序

1. 先实现可解释的确定性规则，验证数据和操作闭环；
2. 积累多订单、不同商品和不同投法的完整矩阵；
3. 建立离线特征生成与策略回放；
4. 使用历史订单训练预测模型；
5. 模型只提供建议，经过稳定性验证后再逐步开放自动操作。

当前数据结构已经能承载时序事实、决策和操作三条时间线。后续模型建设应新增特征
生成和标签模块，不再改变原始事实表的业务口径。
