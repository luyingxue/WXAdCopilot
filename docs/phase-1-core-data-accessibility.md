# 微信视频号量化投流助手

## 第一阶段：核心数据可及性需求与测试台账

**版本：** v0.1  
**日期：** 2026-07-23  
**阶段目标：** 判断系统核心数据是否可稳定、持续、低风险地获取，并确认三端数据能否关联到同一条视频。  
**本阶段边界：** 仅进行只读验证与数据采集，不创建、修改、追加或终止任何投放订单。

---

## 1. 阶段结论标准

第一阶段需要回答五个问题：

1. 能否为每条视频建立稳定的全局标识？
2. 能否持续获取视频流量、互动与关注的累计快照？
3. 能否把商品点击、订单、GMV 和退款归因到单条视频？
4. 能否持续获取微信豆订单的预算、消耗、付费结果和配置？
5. 能否可靠区分或估算自然流量与付费流量？

### 1.1 P0 生死指标

| 编号 | 指标 | 最低可接受条件 | 不满足的影响 |
|---|---|---|---|
| P0-01 | 视频唯一标识 | 流量端、变现端、消耗端至少两端存在可稳定映射的视频 ID | 无法可靠跨库关联 |
| P0-02 | 投放订单唯一标识 | 每笔订单有稳定 `campaign_id/order_id` | 无法支持多次追投与订单级分析 |
| P0-03 | 实际消耗 | 可按订单读取累计消耗及更新时间 | 无法计算 ROI、成本与止损 |
| P0-04 | 付费结果 | 至少可读取付费播放；最好包含付费关注和互动 | 无法判断投放效率 |
| P0-05 | 单视频成交归因 | 可获得单视频订单数、GMV，且归因口径可解释 | 无法计算单视频 GPM/ROI |
| P0-06 | 周期性快照 | 核心累计指标可重复读取并带采集时间 | 无法计算流速、边际变化与衰减 |

### 1.2 可及性等级

| 等级 | 定义 |
|---|---|
| A | 官方接口或官方导出；字段稳定、口径明确 |
| B | 登录态下 XHR/Fetch JSON；可稳定重复读取 |
| C | 页面内嵌数据或 DOM；需要页面结构降级解析 |
| D | 截图/OCR 或人工录入；只能作为补充 |
| X | 当前不可获得 |

## 2. 统一主键与实体模型

### 2.1 必须识别的实体

- 账号：`account_id`、视频号名称、主体、店铺 ID。
- 视频：`video_id/feed_id/object_id`、标题、精确发布时间。
- 投放订单：`campaign_id/order_id`、所投视频 ID、创建时间。
- 商品：`product_id/spu_id/sku_id`、商品名称。
- 交易：`transaction_id/order_id`，如无法获取明细则至少保留聚合口径。
- 快照：`snapshot_time`，表示本地实际采集时刻。

### 2.2 视频关联优先级

1. 三端统一的全局视频 ID。
2. 两端统一 ID，第三端通过稳定映射表关联。
3. `账号 ID + 完整标题 + 精确发布时间` 联合匹配。
4. 标题模糊匹配只用于人工复核，不允许直接驱动自动投流。

### 2.3 关系约束

- 一个账号可有多条视频。
- 一条视频可关联多个商品。
- 一条视频可有多笔投放订单和多次追投。
- 一条视频、商品和投放订单均可有多个时间点快照。
- 每条抓取记录必须保留来源系统、接口/页面、抓取方式和抓取时间。

## 4. 快照与派生指标要求

### 4.1 推荐采集频率

- 投放中的订单与对应视频：每 5–15 分钟。
- 发布 24 小时内、尚未投放的视频：每 15–30 分钟。
- 发布 1–7 天的视频：每 1–3 小时。
- 历史视频与已结束订单：每日回补一次，持续观察退款及归因回写。

实际频率必须根据接口限频、数据刷新延迟和账号风险调整。

### 4.2 核心派生指标

| 指标 | 计算方式 | 备注 |
|---|---|---|
| 播放流速 | 本次总播放 − 上次总播放 | 必须除以实际时间间隔 |
| 流速变化率 | 当前流速/前一窗口流速 − 1 | 用于发现加速或衰减 |
| GPM | GMV/总播放×1000 | 明确使用下单、支付或净 GMV |
| 边际 GPM | 新增 GMV/新增播放×1000 | 适合投中判断 |
| CPM | 消耗/付费播放×1000 | 付费流量成本 |
| 关注成本 | 消耗/付费新增关注 | 仅在有付费关注口径时使用 |
| ROI | 归因 GMV/消耗 | 同时输出毛 ROI 与净 ROI |
| 自然杠杆率 | 撬动自然播放/付费播放 | 优先使用平台官方值 |

### 4.3 自然流量估算边界

若平台不直接提供 `natural_lift_views`，可进行实验性估算：

`估算撬动自然播放 = 投放期总新增播放 − 付费播放 − 预期自然播放`

其中“预期自然播放”应根据投放前多个窗口的自然流速和衰减曲线估计。该结果必须标记为“模型估算”，不得展示为平台精确值，也不得单独作为自动止损依据。

## 5. 单项抓取测试规约

每个模块依次完成以下验证：

1. 人工打开目标页面，确认页面可见字段及账号主体。
2. 记录页面路径、权限角色和是否需要二次扫码。
3. 监听 XHR/Fetch 响应，优先寻找列表接口，再寻找详情接口。
4. 对照页面数值保存脱敏后的关键 JSON 片段。
5. 检查分页、日期范围、排序和筛选参数。
6. 间隔一段时间重复读取，判断数据是否更新。
7. 与官方导出或页面截图进行数值核对。
8. 记录登录态、验证码、限频和接口异常。
9. 若 JSON 不可用，依次降级到页面内嵌数据、DOM、OCR。
10. 更新本台账中的字段名、状态、等级、延迟、风险和结论。

### 5.1 验收阈值

- 唯一键：重复抓取保持一致；不存在同账号内碰撞。
- 数值一致性：与页面或官方导出误差原则上不超过 1%，特殊口径需解释。
- 更新性：能观察到至少一次真实的数据变化。
- 分页完整性：可稳定遍历全部目标记录，无重复、无漏页。
- 可恢复性：登录态失效、网络错误后不会产生重复数据或错误覆盖。
- 只读性：整个测试过程不触发业务状态变更。

## 7. 测试顺序

1. 创作者中心视频列表：优先确认 `video_id`、发布时间和累计播放。
2. 创作者中心视频详情：确认互动、关注、完播、观看时长和更新延迟。
3. 带货短视频明细：确认 `video_fk`、商品、订单、GMV、退款及归因口径。
4. 微信豆订单列表：确认 `campaign_id`、`video_fk`、状态、预算和消耗。
5. 微信豆订单详情：确认付费播放、付费关注、定向配置及自然流量字段。
6. 跨端映射实验：选择 3–5 条视频，验证三端关联准确率。
7. 连续快照实验：对一条正在增长的视频和一笔投放中订单运行 24–72 小时。

## 8. 安全与合规约束

- 第一阶段严格只读，不点击创建、追加、暂停、终止、退款等按钮。
- 不在代码、日志、截图或测试报告中保存明文 Cookie、Token、签名和完整请求头。
- 会话文件与业务数据分开存储，并限制访问权限。
- 所有接口地址和 JSON 示例在共享前进行脱敏。
- 使用保守频率、指数退避和错误熔断，不绕过验证码或平台安全措施。
- 页面或接口发生结构变化时停止自动决策，转入人工复核。
- 生产使用前需进一步核对平台规则、账号授权和数据处理边界。
